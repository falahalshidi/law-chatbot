Detailed Technical Project Report
Project Name: Law Chatbot / Smart Legal Assistant
Report Date: 2026-03-30
Report Status: Based on the current local repository version of the project, including the latest changes currently present, such as the "Resend Approval Email" button from the admin dashboard.

==================================================
1) General Introduction
==================================================

This project is an Arabic web-based system designed to provide a smart legal assistant powered by artificial intelligence and document-retrieval technology (RAG).
The project allows the user to sign up, wait for admin approval, and after approval the user can log in and ask legal questions in Arabic.
The system relies on legal documents uploaded from the admin dashboard. These documents are split into chunks and stored in ChromaDB. Later, these chunks are searched whenever a user asks a question, and the retrieved context is sent to a language model provider to generate an Arabic answer.

The project is not built on standard Supabase Auth. Instead, it uses a custom users table in the database with a custom password_hash field and a custom admin approval workflow specific to this project.

==================================================
2) Functional Objective of the Project
==================================================

The main goal of the system is:

1. To build an Arabic legal Q&A platform.
2. To restrict chat access to approved users only.
3. To provide the administration with a dashboard for reviewing users and managing documents.
4. To provide a retrieval layer over uploaded legal documents.
5. To send an email notification to the user when the account is approved.

In short:
The project combines user management, document management, AI-powered chat, and vector-based retrieval.

4) High-Level Architectural Overview
==================================================

The current architecture consists of four main layers:

Layer 1: Browser / Frontend
- The UI is written in React.
- The user interacts with pages such as: landing page, sign-up, login, chat, and admin dashboard.
- Login state is stored in localStorage under the key user.

Layer 2: Netlify Functions
- This layer represents the server-side API.
- The main functions are:
  - auth: login and account creation
  - admin-users: user management, approvals, and email handling
  - upload-file: uploading, deleting, and listing files
  - chat: retrieving from ChromaDB and requesting the final answer from the AI model provider

Layer 3: Database and Storage
- Supabase Database:
  - users
  - documents
- Supabase Storage:
  - a bucket for storing original uploaded files

Layer 4: AI and Retrieval
- ChromaDB Cloud for storing text chunks
- A chat-completion provider for generating final answers

Overall flow:
The user signs up -> the account becomes pending -> the admin approves -> an approval email is sent -> the user logs in -> asks a question -> the chat function searches ChromaDB -> builds a prompt with context -> sends it to the model provider -> returns the answer.

10) Backend Through Netlify Functions
==================================================

10.1) auth.ts

This function is responsible for:
- login
- signup

Configuration sources:
- SUPABASE_URL
- SUPABASE_SERVICE_ROLE_KEY
- with fallbacks to other keys

Login logic:
1. Read email and password
2. Fetch the user from the users table
3. Verify password_hash using PBKDF2
4. Normalize status through normalizeUserStatus
5. Block login if:
   - rejected
   - pending and not admin
6. Return a compact user object

Signup logic:
1. Verify password confirmation
2. Verify minimum length
3. Prevent duplicate email
4. Generate hash
5. Create a new user in users
6. Set status = pending and is_admin = false

Precise note:
verifyPassword also supports a legacy case when the stored value does not include ":" and directly compares the password in plain text.
This means there is implicit support for legacy passwords that were not hashed.

10.2) admin-users.ts

This function is responsible for:
- GET: fetch all users
- PATCH: modify user status, admin role, or resend email

Possible updates:
- status: accepted / rejected
- isAdmin: true / false
- resendApprovalEmail: true

Approval behavior:
- when a user is switched to accepted, is_approved is also updated
- if the user becomes accepted for the first time and is not an admin, the function attempts to send an approval email

Resend behavior:
- allowed only if the user is accepted
- not allowed for admin accounts

The function returns:
- success
- emailNotification if available

10.3) upload-file.ts

This is one of the most important functions in the project.

Supported operations:
- GET: list files
- POST: upload a new file
- DELETE: delete a file

Listing files:
- it first tries to fetch metadata from the documents table
- then fetches files from ChromaDB
- merges both sources into one list

Upload flow:
1. Receive base64, filename, type, size, and uploadedBy
2. Convert base64 into Buffer
3. determine file type
4. extract text:
   - PDF via pdf-parse
   - DOCX via mammoth
   - TXT/MD via toString
5. reject the file if no text exists
6. split text into chunks of size 1000 with overlap 200
7. classify the document via detectCategory
8. ensure the bucket exists in Supabase Storage
9. store the original file in Storage
10. store metadata in the documents table
11. create metadata for each chunk
12. store the chunks in ChromaDB

Delete flow:
1. delete the original file from Supabase Storage if it exists
2. delete metadata from documents
3. delete all related chunks from ChromaDB

Important architectural note:
There is no unified transaction across:
- Supabase Storage
- the documents table
- ChromaDB

Therefore, partial inconsistency may happen if one part succeeds and another fails.

10.4) chat.ts

This function is the core of the assistant.

Execution stages:

1. receive messages from the frontend
2. verify the existence of the last user message
3. return a short direct reply for simple greetings
4. search ChromaDB through searchRelevantDocuments
5. build context from retrieved results
6. build an Arabic system prompt
7. send the request to the chat API provider
8. return the generated text as JSON

Search mechanism:
- the question is classified through detectCategory
- the query is expanded with category hints
- if the category-specific search returns too few results, it falls back to a broader search

Context-building mechanism:
- sort documents by distance
- remove duplicates
- trim each document to around 600 characters
- enforce a total context size limit around 2500 characters

Answer generation mechanism:
- if context exists:
  - instruct the model to prefer retrieved context
  - answer in Arabic only
  - answer directly and proportionally to the question
- if no context exists:
  - instruct the model to give the best possible answer without mentioning that the database lacks information

Important note:
Although the frontend sends history, the server forwards only:
- the system prompt
- the current user query

So real multi-turn memory is not active in the final prompt.

10.5) law-library.ts

This function powers the internal law library feature.

Supported behavior:
- GET all available legal documents
- GET searched documents using a query parameter q
- GET a single document's reconstructed full text using documentId or filename

What it does:
1. load document metadata from the documents table
2. load document chunk information from ChromaDB
3. merge both views into a unified document list
4. if q is present:
   - perform direct matching by filename/category/type
   - perform semantic search in ChromaDB
   - generate snippets from matching chunks
5. if documentId or filename is present:
   - fetch all chunks for that document
   - sort by chunkIndex
   - join chunks into fullText

Functional result:
This endpoint enables users to browse and read uploaded legal documents directly inside the product.

13) End-to-End Operational Flows
==================================================

13.1) Sign-up flow

1. The user opens /signup
2. enters email and password
3. the frontend sends POST to /api/auth
4. auth.ts validates input
5. generates the password hash
6. inserts the user into users with pending state
7. the frontend shows a success message

13.2) Login flow

1. The user opens /login
2. submits email and password
3. auth.ts fetches the user and verifies the hash
4. if status is pending:
   - returns PENDING_APPROVAL
5. if status is rejected:
   - returns REJECTED_ACCOUNT
6. if accepted:
   - returns user
7. the frontend stores user in localStorage

13.3) User approval flow

1. The admin opens /admin
2. AdminPage requests GET /api/admin-users
3. the user list is displayed
4. the admin clicks "Approve"
5. PATCH /api/admin-users with status=accepted
6. admin-users.ts updates status and is_approved
7. it tries to send the approval email
8. the frontend shows success or an email failure message

13.4) Resend email flow

1. The user is already accepted
2. A "Resend Email" button appears in that user row inside the admin dashboard
3. When clicked:
   - PATCH /api/admin-users with resendApprovalEmail=true
4. The function sends the email without changing status

13.5) File upload flow

1. The admin selects a file or drags it into the page
2. the browser converts it to base64
3. POST /api/upload-file
4. the server extracts text
5. splits it into chunks
6. classifies it
7. stores the original file in Supabase Storage
8. stores metadata in documents
9. stores the chunks in ChromaDB

13.6) Asking a question in chat

1. The user writes a question
2. LegalChatbotPage adds the user message locally
3. sends it to /api/chat
4. chat.ts searches for relevant chunks
5. builds a prompt
6. calls the AI provider
7. returns the answer
8. the frontend renders it as an assistant message

13.7) File deletion flow

1. The admin clicks delete
2. the browser requests confirmation using confirm
3. DELETE /api/upload-file
4. the server deletes from:
   - Supabase Storage
   - documents
   - ChromaDB

13.8) Internal law browsing flow

1. The user logs in and lands on /chat
2. clicks "Search Laws"
3. opens /laws
4. the frontend loads available legal files through /api/law-library
5. the user can search by term
6. the frontend requests search results
7. the user selects a law
8. the page loads and reconstructs the full text from stored chunks
9. the user can read the law directly in the platform or move to /assistant with a prefilled law-related prompt

15) Security Perspective and Current Technical Risks
==================================================

This is one of the most important sections of the report from a professional point of view.

1. Admin protection is not truly enforced on the server
The frontend only prevents non-admin users from seeing /admin.
But functions such as:
- /api/admin-users
- /api/upload-file
- /api/law-library
do not verify the requester's identity or permissions at the server level.
Anyone who can directly access the endpoint may be able to perform administrative operations if there is no extra protection outside the application.

2. localStorage is used as the identity/session source
This is acceptable for a prototype, but it is not a secure production authentication system.
There is no signed token, no refresh flow, and no session verification on each request.

3. Sensitive fallback keys or default values exist
Some files contain fallback values or legacy defaults that are not ideal, increasing the risk of leakage or configuration confusion.

4. There is no transaction across the three systems
File upload depends on:
- Storage
- Database
- ChromaDB
without a unified transaction.
If one part fails after another succeeds, partial inconsistency can occur.

5. History is not actually used in the final prompt
This is not a security issue, but it limits the quality of multi-turn conversations.

6. There is legacy and partially unused code
Examples:
- src/lib/password.ts
- src/lib/chromadb.ts
- src/components/ui/chatgpt-prompt-input.tsx
- legacy Pinecone-related parts

This increases cognitive load for any new developer joining the project.

7. index.html is not configured for Arabic
This is a small issue, but it affects SEO, direction, and some accessibility/tooling behavior.

8. README is not fully aligned with the current state
For example, it mentions Tailwind CSS 4 while package.json uses Tailwind 3.4.1.

==================================================
17) Current Limitations and Technical Debt
==================================================

1. The system is not secure enough for production because server-side permission checks are missing.
2. Session management is primitive.
3. There are no visible automated tests in the project.
4. There is no clearly separated service/repository layer in either frontend or backend.
5. Some experimental or old code is still present.
6. The chat logic does not use real conversational memory despite the frontend sending history.
7. Document classification is based only on simple keywords.
8. There is no clearly structured observability layer for logs/metrics/monitoring.

==================================================
18) Future Improvement Suggestions
==================================================

1. Implement real server-side security
- use verified JWT or Supabase Auth or a backend session system
- block all admin operations unless the admin identity is explicitly verified

2. Separate business logic more clearly
- create service layers for backend functions
- separate storage logic from retrieval logic

3. Improve multi-turn conversation quality
- pass actual conversation history into the final prompt

In its current state, the project is a practical and usable advanced prototype or MVP for an Arabic legal assistant, with:
- user registration
- admin approval
- email notifications
- legal document upload
- retrieval from ChromaDB
- AI-generated Arabic answers
