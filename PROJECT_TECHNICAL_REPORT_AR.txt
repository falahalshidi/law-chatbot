التقرير التقني التفصيلي للمشروع
اسم المشروع: Law Chatbot / المساعد القانوني الذكي
تاريخ إعداد التقرير: 2026-03-30
حالة التقرير: مبني على نسخة المشروع الحالية داخل المستودع المحلي، ويشمل آخر التعديلات الموجودة حاليًا مثل زر إعادة إرسال بريد القبول من لوحة الأدمن.

==================================================
1) مقدمة عامة
==================================================

هذا المشروع عبارة عن نظام ويب عربي يهدف إلى تقديم مساعد قانوني ذكي يعتمد على الذكاء الاصطناعي وتقنية الاسترجاع من المستندات RAG.
المشروع يسمح للمستخدم بالتسجيل، ثم انتظار موافقة الإدارة، وبعد القبول يمكنه تسجيل الدخول وطرح أسئلة قانونية باللغة العربية.
النظام يعتمد على مستندات قانونية يتم رفعها من لوحة الأدمن، ثم تقسيمها إلى أجزاء وتخزينها في ChromaDB، وبعدها يتم البحث في هذه الأجزاء عند كل سؤال، ثم إرسال السياق المسترجع إلى مزود نموذج لغوي لإنتاج إجابة عربية.

المشروع ليس مبنيًا على Supabase Auth التقليدي، بل يستخدم جدول users مخصصًا داخل قاعدة البيانات مع password_hash مخصص ونظام موافقة إداري خاص بالمشروع.

==================================================
2) الهدف الوظيفي للمشروع
==================================================

الهدف الرئيسي من النظام هو:

1. بناء منصة أسئلة وأجوبة قانونية باللغة العربية.
2. تقييد الوصول إلى الشات للمستخدمين المقبولين فقط.
3. إعطاء الإدارة لوحة تحكم لمراجعة المستخدمين وإدارة الوثائق.
4. توفير طبقة استرجاع معرفي من مستندات قانونية مرفوعة.
5. إرسال إشعار بريد إلكتروني للمستخدم عند قبول حسابه.

باختصار:
المشروع يجمع بين إدارة مستخدمين، إدارة مستندات، ذكاء اصطناعي للمحادثة، واسترجاع من قاعدة متجهات.

==================================================
4) نظرة معمارية عالية المستوى
==================================================

المعمارية الحالية تتكون من أربع طبقات رئيسية:

الطبقة الأولى: المتصفح / Frontend
- الواجهة مكتوبة بـ React.
- المستخدم يتفاعل مع الصفحات: الصفحة الرئيسية، التسجيل، الدخول، الشات، لوحة الأدمن.
- حالة تسجيل الدخول محفوظة في localStorage تحت المفتاح user.

الطبقة الثانية: Netlify Functions
- هذه الطبقة تمثل API السيرفر.
- الدوال المهمة:
  - auth: تسجيل الدخول وإنشاء الحساب
  - admin-users: إدارة المستخدمين والموافقات والبريد
  - upload-file: رفع الملفات، حذفها، سردها
  - chat: تنفيذ الاسترجاع من ChromaDB ثم طلب الإجابة من نموذج الذكاء الاصطناعي

الطبقة الثالثة: قاعدة البيانات والتخزين
- Supabase Database:
  - users
  - documents
- Supabase Storage:
  - bucket لحفظ النسخة الأصلية من الملفات

الطبقة الرابعة: الذكاء الاصطناعي والاسترجاع
- ChromaDB Cloud لتخزين المقاطع النصية
- مزود chat completion لإنتاج الإجابة النهائية

تدفق العمل العام:
المستخدم يسجل -> الحساب يدخل pending -> الأدمن يوافق -> يصل بريد قبول -> المستخدم يسجل دخول -> يسأل سؤالًا -> function chat تبحث في ChromaDB -> تبني prompt مع السياق -> ترسل لمزود النموذج -> تعيد الإجابة.

==================================================
10) الباكند عبر Netlify Functions
==================================================

10.1) auth.ts

هذه الدالة مسؤولة عن:
- login
- signup

مصادر الإعداد:
- SUPABASE_URL
- SUPABASE_SERVICE_ROLE_KEY
- أو fallback إلى مفاتيح أخرى

منطق login:
1. قراءة البريد وكلمة المرور
2. جلب المستخدم من جدول users
3. التحقق من password_hash عبر PBKDF2
4. تطبيع status عبر normalizeUserStatus
5. منع الدخول إذا:
   - rejected
   - pending وليس أدمن
6. إرجاع user object مختصر

منطق signup:
1. التحقق من تطابق كلمة المرور
2. التحقق من الحد الأدنى للطول
3. منع التكرار في البريد
4. توليد hash
5. إنشاء مستخدم جديد في users
6. ضبط status = pending و is_admin = false

ملاحظة دقيقة:
verifyPassword تدعم أيضًا حالة قديمة إذا كان stored لا يحتوي ":"، حيث تقارن كلمة المرور plain text.
هذا يعني أن هناك دعمًا ضمنيًا لكلمات مرور legacy غير مهيأة بالهاش.

10.2) admin-users.ts

هذه الدالة مسؤولة عن:
- GET: جلب كل المستخدمين
- PATCH: تعديل حالة المستخدم أو صفة الأدمن أو إعادة إرسال البريد

التحديثات الممكنة:
- status: accepted / rejected
- isAdmin: true / false
- resendApprovalEmail: true

سلوك القبول:
- عند تحويل المستخدم إلى accepted يتم أيضًا تحديث is_approved
- إذا تحوّل لأول مرة إلى accepted وكان غير أدمن، تحاول الدالة إرسال بريد القبول

سلوك إعادة الإرسال:
- يسمح فقط إذا كان المستخدم accepted
- لا يسمح به لحسابات الأدمن

ترجع الدالة:
- success
- emailNotification إن وجد

10.3) upload-file.ts

هذه من أهم دوال المشروع.

الوظائف المدعومة:
- GET: سرد الملفات
- POST: رفع ملف جديد
- DELETE: حذف ملف

سرد الملفات:
- يحاول أولًا جلب metadata من جدول documents
- ثم يجلب الملفات من ChromaDB
- يدمج النتيجتين في قائمة واحدة

رفع الملف:
1. استقبال base64 واسم الملف ونوعه وحجمه و uploadedBy
2. تحويل base64 إلى Buffer
3. تحديد نوع الملف
4. استخراج النص:
   - PDF عبر pdf-parse
   - DOCX عبر mammoth
   - TXT/MD عبر toString
5. رفض الملف إذا لم يوجد نص
6. تقسيم النص إلى chunks بحجم 1000 حرف مع overlap 200
7. تصنيف المستند عبر detectCategory
8. التأكد من وجود bucket في Supabase Storage
9. حفظ النسخة الأصلية في Storage
10. حفظ metadata في جدول documents
11. إنشاء metadata لكل chunk
12. تخزين المقاطع في ChromaDB

حذف الملف:
1. حذف النسخة الأصلية من Supabase Storage إن وجدت
2. حذف metadata من documents
3. حذف كل المقاطع المرتبطة من ChromaDB

ملاحظة معمارية مهمة:
لا توجد transaction موحدة بين:
- Supabase Storage
- documents table
- ChromaDB

لذلك قد يحدث عدم اتساق جزئي إذا فشل أحد الأجزاء بعد نجاح الآخر.

10.4) chat.ts

هذه الدالة هي قلب المساعد القانوني.

مراحل التنفيذ:

1. استقبال messages من الواجهة
2. التحقق من وجود آخر رسالة user
3. رد سريع على التحيات البسيطة
4. البحث في ChromaDB عبر searchRelevantDocuments
5. بناء context من النتائج المسترجعة
6. بناء system prompt بالعربية
7. إرسال الطلب إلى مزود chat API
8. إعادة النص الناتج بصيغة JSON

آلية البحث:
- يتم تصنيف السؤال عبر detectCategory
- يتم توسيع الاستعلام بكلمات دلالية من نفس الفئة
- إذا كانت نتائج البحث قليلة في التصنيف المحدد، يتم fallback إلى بحث عام

آلية بناء السياق:
- ترتيب المستندات حسب distance
- إزالة التكرارات
- قص كل مستند تقريبًا إلى 600 حرف
- تحديد حد إجمالي للسياق يقارب 2500 حرف

آلية توليد الإجابة:
- إذا وجد context:
  - يطلب من النموذج تفضيل السياق المسترجع
  - الإجابة بالعربية فقط
  - الإجابة مباشرة ومتناسبة مع السؤال
- إذا لم يوجد context:
  - يطلب من النموذج تقديم أفضل إجابة ممكنة دون ذكر نقص قاعدة البيانات

ملاحظة مهمة:
رغم أن الواجهة ترسل history، إلا أن السيرفر يمرر فقط:
- system prompt
- current user query

أي أن الذاكرة الحوارية الحقيقية ليست مفعلة على مستوى prompt النهائي.

13) تدفق العمليات التشغيلية End-to-End
==================================================

13.1) تدفق إنشاء حساب

1. المستخدم يفتح /signup
2. يدخل البريد وكلمة المرور
3. الواجهة ترسل POST إلى /api/auth
4. auth.ts يتحقق من المدخلات
5. ينشئ hash
6. يضيف المستخدم في users بالحالة pending
7. الواجهة تعرض رسالة نجاح

13.2) تدفق تسجيل الدخول

1. المستخدم يفتح /login
2. يرسل البريد وكلمة المرور
3. auth.ts يجلب المستخدم ويتحقق من الهاش
4. إذا كان pending:
   - يرجع PENDING_APPROVAL
5. إذا كان rejected:
   - يرجع REJECTED_ACCOUNT
6. إذا accepted:
   - يرجع user
7. الواجهة تخزن user في localStorage

13.3) تدفق قبول المستخدم

1. الأدمن يفتح /admin
2. AdminPage يطلب GET /api/admin-users
3. تظهر قائمة المستخدمين
4. الأدمن يضغط "الموافقة"
5. PATCH /api/admin-users مع status=accepted
6. admin-users.ts يحدث status و is_approved
7. يحاول إرسال بريد القبول
8. الواجهة تعرض نجاحًا أو رسالة فشل بريد

13.4) تدفق إعادة إرسال البريد

1. المستخدم صار accepted مسبقًا
2. يظهر زر "إعادة إرسال البريد" في صفه داخل لوحة الأدمن
3. عند الضغط:
   - PATCH /api/admin-users مع resendApprovalEmail=true
4. الدالة ترسل البريد بدون تغيير status

13.5) تدفق رفع ملف

1. الأدمن يختار ملفًا أو يسحبه
2. المتصفح يحوله إلى base64
3. POST /api/upload-file
4. السيرفر يقرأ النص
5. يقسمه إلى chunks
6. يصنفه
7. يحفظ الأصل في Supabase Storage
8. يحفظ metadata في documents
9. يحفظ المقاطع في ChromaDB

13.6) تدفق السؤال داخل الشات

1. المستخدم يكتب سؤالًا
2. LegalChatbotPage تضيف رسالة user محليًا
3. ترسل إلى /api/chat
4. chat.ts يبحث عن مقاطع مشابهة
5. يبني prompt
6. يستدعي مزود الذكاء
7. يعيد الإجابة
8. الواجهة تعرضها كرسالة assistant

13.7) تدفق حذف ملف

1. الأدمن يضغط حذف
2. المتصفح يطلب تأكيد confirm
3. DELETE /api/upload-file
4. السيرفر يحذف من:
   - Supabase Storage
   - documents
   - ChromaDB

15) الجانب الأمني والمخاطر التقنية الحالية
==================================================

هذه أهم نقطة في التقرير من الناحية المهنية.

1. حماية الأدمن غير مطبقة على السيرفر بشكل حقيقي
الواجهة فقط تمنع المستخدم غير الأدمن من رؤية /admin.
لكن Functions مثل:
- /api/admin-users
- /api/upload-file
لا تتحقق من هوية المستدعي أو صلاحياته على مستوى السيرفر.
أي شخص يستطيع الوصول للنقطة مباشرة قد يتمكن من تنفيذ عمليات إدارية إن لم توجد طبقات حماية خارجية.

2. الاعتماد على localStorage كهوية جلسة
هذا مناسب كنموذج أولي، لكنه ليس نظام auth آمنًا للإنتاج.
لا يوجد token signed، ولا refresh flow، ولا session verification لكل request.

3. وجود fallback لمفاتيح حساسة أو قيَم افتراضية
بعض الملفات تحتوي fallback values غير مثالية أو legacy values، وهذا يزيد مخاطر التسريب أو الالتباس في الإعدادات.

4. عدم وجود transaction عبر الأنظمة الثلاثة
رفع الملف يعتمد على:
- Storage
- Database
- ChromaDB
بلا transaction موحدة.
إذا فشل جزء ونجح جزء آخر قد ينتج عدم اتساق.

5. history لا تستخدم فعليًا في prompt النهائي
هذا ليس خطرًا أمنيًا، لكنه يحد من جودة المحادثة متعددة الجولات.

6. وجود أكواد legacy وغير مستخدمة
مثل:
- src/lib/password.ts
- src/lib/chromadb.ts
- src/components/ui/chatgpt-prompt-input.tsx
- أجزاء Pinecone legacy
وهذا يزيد الحمل المعرفي على أي مطور جديد.

7. index.html غير مضبوطة للغة العربية
مشكلة بسيطة لكنها تؤثر على SEO والاتجاه وتجربة بعض الأدوات المساعدة.

8. README غير مطابق بالكامل للوضع الفعلي
يوجد ذكر لـ Tailwind CSS 4 بينما package.json يستخدم Tailwind 3.4.1.
